# Plans

Puck is an engine that runs authored Puck programs on generic machinery. Worlds, rules, cameras, motion, games and cartridges are `.puck` documents an author owns; the engine's C# compiles, runs, schedules, costs and draws them, and never implements one of them as a feature. The machines that run cartridges are that machinery too: an emulator core is a VM, as the SDF VM is. Every concrete design, the standard included, is data in `worlds/standard/` that any author imports, overrides by id or replaces; the debug world develops it and holds only its own exhibits. A design written into C#, or living only in the debug world, is built twice and is removed when found.

The goals, in the order a conflict is settled:

1. **Authors rule.** The engine offers mechanisms; a C# default, enum value or constant that encodes a look or a feel is a second implementation. A plan that would build a feature in C# where a program could express it is rewritten to build the mechanism and author the program.
2. **Quality and performance together, at the slowest frame.** The bars are the worst frame at the highest quality, read in motion on each device's own path and in both topologies, local and against the hosted authority: the RTX 4070 at 2560 by 1440 and the RTX 2060 at 1920 by 1080 at 60 FPS, the Steam Deck at 45 ([AGENTS.md](../../AGENTS.md), [the register](../decisions/rendering.md#the-pipeline-foundation)). The 4070 meets them first. The 2060 is a consumer release target: it runs only the player build with prewarmed caches, installed through the player channel, and never builds or cold-bakes, so its readings measure what a player gets. A cost is removed at its cause. A lower tier, a coarser shadow snap, a frame of latency, fewer octaves of contact or a capped view is never the fix for a missed bar, and no plan keeps such a lever in reserve.
3. **Determinism pins the mapping.** Fixed-point simulation; the same document and input give bit-identical state on every machine, backend and thread count. A deliberate correction moves hashes and re-records them in the same change. Nothing presentation-side (who looks, what is resident) may change simulation state.
4. **Velocity, and rapid iteration first among the fundamentals.** An author's small edit shows in the running World in seconds, without a rebuild, a cold bake or a relight of what it did not change, and every edit loop is timed from the edit to its first and settled frames ([the iteration plan](iteration.md)). Two forcing functions keep the longer waits honest: about half a minute from an engine C# or HLSL edit to seeing it, and about a minute to bake the debug world from an empty store, per backend, on the lead machine. They are pressures to judge changes by, not finish lines. Work is proportional to change. Derived products are caches keyed from the code that derives them: never committed, never compared by a gate, and shipped prewarmed in the player build.
5. **One implementation per mechanism.** Find the system before building one; merge the second when found; a plan that would add a second scheduler, selector, overlay writer, costing model or contact solver is redirected to the one that exists.
6. **Fundamentals, driven by features.** Frame time, bake time, build time and duplication are the core of the work, and features built on the engine's systems are a primary way to stress and improve them ([AGENTS.md](../../AGENTS.md)). Feature work that rests on a fundamental about to change (threading, residency, the bake, state storage) is reshaped into an input to that change, or waits for it.

**The engine job system is the path for frame time, background work and memory ownership** ([its packet](open-items.md#engine-job-system)). One prioritised scheduler under a frame budget runs frame-critical work, then a deterministic parallel tick over fixed partitions committed in a fixed order, then parallel view recording on both backends, then background bake and GI proportional to what changed. The structural step ahead of its build order is where the tick runs: the in-process authority steps on the frame thread today, so a frame costs the tick plus the produce, and [the CPU frame](open-items.md#the-cpu-frame) moves the step to its own thread behind a design. Its first value is scheduling: the quiet machine's slow frames are a 30 Hz tick and a 15 Hz rated presentation burst meeting on one frame, with bodies no view can see still posing and probing, so the scheduler first spreads rated work off tick frames, holds unseen work and makes work proportional to visibility; the parallel tick (the snapshot, crossing scan and rigid bodies today; kit-body advance needs the per-partition kit transaction) and parallel recording come second. It owns memory as well: per-job and per-partition scratch ownership, borrowing and handoff; one physical byte-accounting owner that residency, caches and jobs consume; and which storage moves to native memory through the existing allocator (`IAllocator`, `MimallocAllocator`). The immediate garbage-collection cuts are owned-storage reuse on today's runtime and lead the frame-time work; the custom no-GC runtime port is later work. The job system accelerates authored programs generically: it schedules and parallelises rule and motion-program execution, and does not hand-write a feature to make it fast. Everything that schedules work (the mesh bake, the irradiance trace, residency's near-first order, search's spare budget, machine stepping) is a consumer of this scheduler that supplies priority and policy, never a second executor. The memo that designs the scheduler also fixes the state/jobs contract (partitions, read epochs, commit and allocation order, partition-owned scratch), because parallel evaluation changes rule-read semantics and that mapping is chosen, not inherited.

How the programmes serve this. **Iteration** is the first fundamental: the compile, the reload and the bake each do work in proportion to what an edit reached, measured edit to frame by `world.iteration`. **Rendering** is baked meshes rasterised with shadow cascades and an irradiance volume traced and relit on the GPU. The frame walks no field. Its open work is the bake's latency (the bake kernel is a small share of a cold bake's wall time, so the CPU stages, store traffic and scheduling between dispatches are the cost), its managed garbage, GI scheduling, and view recording under the job system. **The valley and the terrain pass** are the engine's live test of quality at the bar: terrain-scale relief, one certified contact on the drawn rock, an image exposure meter, haze and far shadows, with the two material sets authored in the standard. **State and language** converge on one live store, one write door, one deterministic work allowance and pools of records. **Residency and memory** supply demand, priority, eviction and byte accounting to the scheduler. **Play, machines, runtime and the editor** are the engine's consumers: they prove themselves on the debug world, the one live world, and their feature waves follow the fundamentals. Local games reveal the MMO ([the ruling](../decisions/play.md)), so every world runs well both on a player's machine and against the hosted authority, and the server's scale work (interest, deltas, per-row stepping, durable storage) is ordinary work, not a later phase. **Delivery** reaches players through the player channel: the lead machine produces the prewarmed caches, CI releases what is pushed to `main`, and the launcher installs and updates the player build. **UI and input** stay generic mechanisms with authored skins and vocabularies.

**How the work is ordered now** (the owner's rulings). Structural change is the aim: a system whose shape is the limit is replaced by the better architecture, and tuning it comes only where no structural answer exists ([AGENTS.md](../../AGENTS.md)). The bounds that keep the performance targets from being met come first, and the development and testing the MMO work needs is interleaved with them and never starved, because it is how the performance work is measured and proved in the topology that matters. Two milestones give that work its shape: the debug world hosted on Azure with the RTX 2060 playing in it as a consumer, and four-player split screen on the RTX 4070 with all four seats joined to one remote host. The debug world also has to stress the idea it proves, so it gains a town, crowds of connected players, a moon on another authority and live authoring on the hosted world. Every plan is read through one question: what does this become with hundreds of bodies and a hub of a dozen live worlds? [Open items](open-items.md#next) ranks the work by these rules.

Where the programmes compete: a tuning of a system whose shape is the limit against its replacement, the replacement wins; a feature wave against a fundamental, the fundamental wins and the feature becomes a sizing input to the memo; a quality trade against a cause fix, the cause fix wins; a per-programme scheduler, selector, budget or memory track against the engine's one, the engine's wins and the programme keeps the policy; a thread against work that should not run at all, the scheduling fix wins, because work proportional to visibility removes what a thread would only divide; a forcing world in `experimental/` against the debug world, the debug world wins; a test or recorded artifact against a change, the change wins and the artifact is re-recorded or deleted.

## How the pages divide

This directory holds the work that remains to be scheduled. Current architecture lives in the owner documents under `docs/architecture/`, and the reasoning behind each choice in [the decision registers](../decisions/README.md).

- **[Open items](open-items.md) is the queue**: one ranked Next list, the work beside it, every open owner decision, and the work packets, each one lane's worth of defects and leads. It is the only place that ranks work across programmes.
- **A plan holds one programme's open work**: its decisions still to build, its steps, and the check that closes each. A plan states what its steps depend on, never a rank among programmes, and never a second list of what is next.
- **This page is the only index of the plans.** A new plan is added here in the change that creates it, and a finished one leaves in the change that deletes it.
- **A step id is unique within its plan.** Outside the plan, cite the plan's name or a link with the id.
- **A research round's reports are records, not plans.** They are snapshots with no step, queue or owner call, and they lose to the decision and the code. They live in a folder beside the plan they feed only while that plan has open steps. The change that closes the plan writes the sources its decision rests on into the decision and deletes the folder. A review of a memo is deleted once its findings are answered.

A plan's citations are evidence about the code they were written against; recheck the code before scheduling work from them. Every forcing artifact and check runs on the debug world. The quilt, the island and the One World stay quarantined in `experimental/`; what they have that the debug world lacks is ported into it ([the port packet](open-items.md#port-the-experimental-worlds-missing-features)).
