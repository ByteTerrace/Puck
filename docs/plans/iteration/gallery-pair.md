# Gallery pair sessions

How the owner and the lead iterate on the gallery together in real time, at
minutes per sweep (rapid iteration is the gallery work's primary goal, the
owner's ruling), once the overhaul's vertical slice is in. The owner is the
critic, watching the live window; the lead edits the source and reads the
World. Every edit lands in the running World through the loops
[iteration](../iteration.md) times, with no restart and no cold bake.

## The loop

1. The owner names what reads wrong at a viewpoint.
2. The lead edits the `.puck` source in the main checkout: the gallery module
   (`worlds/debug/gallery/`), the kit (`worlds/standard/architecture.puck`)
   or the exhibits (`worlds/debug/shapes.puck`).
3. `world.watch on` reloads the saved source 150 ms after the save
   (`WorldViewGraphHost.WatchDebounceMilliseconds`). The World runs the main
   checkout's sources, so a saved edit shows in that same window.
4. The owner judges the result live. When asked, the lead captures every
   bookmark into one sheet beside the reference panels.

Rows generated by a template or a `for` can't be written back by `world.save`
([sdf-authoring](../../../.claude/skills/sdf-authoring/SKILL.md#the-loop)), and
the kit is templated throughout. So pair edits go to the source file, never
through `world.row.set` plus `world.save`. A throwaway live tweak with
`world.row.set` is still the fastest way to try a value before writing it.

## What each edit should cost

| Edit | Path | Expected |
|---|---|---|
| A colour, roughness, emission or paint value | a presentation install, no bake | a frame in a second or two |
| A shape's size or position in one kit piece | a rebake of that creation's groups, coarse tier first | seconds |
| A placement moved, added or removed | a rebake of the placements touched | seconds |
| A light or exposure value | no bake | a frame in a second or two |
| The time of day | `world.state.cell.set day $value <t>` with the advance held | immediate; lighting reconverges |

The `lit` stage (the irradiance volume converged) has been the slow one: 117
to 181 seconds after a boot. A sweep doesn't wait for `lit`. The owner judges
form and material at `shown`, and lighting once the volume around the edit has
relit.

## Before the session

- **The machine is the session's.** No other windowed World and no heavy suite
  runs during a pair session; running lanes keep to code and headless work.
  GPU admission waits are the largest avoidable delay.
- **A warm World, booted once.** The lead boots the gallery root
  (`worlds/debug/gallery-root.puck`, or the debug world when the view out
  matters) on the slice's commit before the session, lets it bake and settle,
  and keeps that one World for the whole session. A restart is a bake and a
  settle; an edit is not. When a merged change needs a restart (engine code,
  shaders, or a reload that says `restart owed`), the lead restarts without
  asking (the owner's standing instruction for pair sessions): `world.pins save`
  before it and `world.pins restore` after it (or `pins: true` on
  `puck_world_stop` and `puck_world_start`) bring back the window's size and
  place, the held time, the exposure pin, the camera, the seat's registers
  (noclip among them) and its pose. The lead says what changed.
- **Owner input** on the same World: `ownerPlay` (`--devices all`) when the
  owner wants to walk it.
- **Bookmarks.** Named camera poses that match each reference panel (the
  eye-level hall, a plinth close, the arcade, a window bay, the atrium), and
  the time pinned (`day` 0.5, plus an afternoon reading), so each sweep
  captures the same views.
- **The loops read on the slice.** One edit of each kind above, timed with
  `world.iteration` on the gallery root, so the session knows its real
  costs. A loop that takes minutes is an engine gap, fixed before the session.

## Gaps known to cost a sweep

- Hardware-ray probe hits read material 0 from released mesh words, which
  tints interiors orange (open items, Lighting and GI). The fix is in
  progress.
- Glossy floors reflect the room through the screen-space `views-reflections`
  pass, with the probes behind it. It is over its frame-budget share
  ([the frame budget](../frame-budget.md), step 5) and is being optimized
  rather than trimmed: the owner's ruling is that it must perform well, with
  no corners cut.
- The gallery root has no valley around it, so its windows show white. View-out
  judgements happen in the debug world.

## Gaps found in the first live session

Measured on the gallery root, warm, with `world.watch on` (`world.iteration` per reload):

- **A palette colour edit is not consistently a presentation-only install.** The first edit to the plinth's screen
  colour took 5.9 s to its first frame and 6.8 s to meshes, as if the creations rebaked. Later edits of the same
  value reached their first frame in 0.54 to 0.55 s. Find what the first reload rebuilt.
- **An emissive edit relights the whole volume.** `lit` trailed by about 40 s after the screen's emissive changed,
  so lighting can't be judged until the volume settles.
- **An exposure pin and a named camera across a reload, unconfirmed live.** In the first session the exposure pin was
  gone after a reload (the hall washed out) and an active `view.override camera <name>` kept its old rig until
  re-selected. The `world.exposure pin` lever and the composition overrides live outside the document and a reload
  does not touch them; a named camera's rig compiles again when its `cameras` row moves
  (`WorldCameraRigCompiler.Cache.Resolve`). A headless reload keeps the free camera, a held clock and a seat's pose.
  Still owed: a windowed check of both. If the pin was the gallery's inspection lever (`gallery.inspect`, whose
  `galleryFill.hold` cell drives `render.exposure.hold`), a reload that changes any cell of `galleryFill` re-seeds the
  whole row (`WorldDocument.NameReloadEdit` works by row), so carrying the live value of each cell whose seed did not
  change is the fix.
- **`world.view.camera` reports the seat's chase camera**, not an active camera override, so it can't confirm what
  the window shows.
- **A static view is never still.** With the camera, lighting and exposure held, about 9% of pixels change every
  frame (peaks of 184 levels), which makes small edits harder to judge by comparing frames.
- **A C# edit costs a full restart:** a build of `Puck.World`, a boot, and the bakes settling (about 17 s from boot
  on a warm store). There's no hot path for engine code yet.
- **Duplicated look values defeat edits.** The display screen's colour was written twice (the plinth kit and the
  screen overlay in `shapes.puck`), so editing the kit changed nothing on screen. The overlay now reads the kit's
  material.

Found in the grid and toybox session:

- **Window size needed a restart**: fixed during the session; `world.window` sizes, centres and moves the live window.
