# Gallery pair sessions

How the owner and the lead iterate on the gallery together in real time, at
minutes per sweep, once the overhaul's vertical slice is in. The owner is the
critic, watching the live window; the lead edits the source and reads the
World. Every edit lands in the running World through the loops
[iteration](../iteration.md) times, with no restart and no cold bake.

## The loop

1. The owner names what reads wrong at a viewpoint.
2. The lead edits the `.puck` source in the main checkout: the gallery module
   (`worlds/debug/gallery/`), the kit (`worlds/standard/architecture.puck`)
   or the exhibits (`worlds/debug/shapes.puck`).
3. `world.watch on` reloads the saved source 150 ms after the save
   (`WorldViewGraphHost.WatchDebounceMilliseconds`). The World runs the main
   checkout's sources, so a saved edit shows in that same window.
4. The owner judges the result live. When asked, the lead captures every
   bookmark into one sheet beside the reference panels.

Rows generated by a template or a `for` can't be written back by `world.save`
([sdf-authoring](../../../.claude/skills/sdf-authoring/SKILL.md#the-loop)), and
the kit is templated throughout. So pair edits go to the source file, never
through `world.row.set` plus `world.save`. A throwaway live tweak with
`world.row.set` is still the fastest way to try a value before writing it.

## What each edit should cost

| Edit | Path | Expected |
|---|---|---|
| A colour, roughness, emission or paint value | a presentation install, no bake | a frame in a second or two |
| A shape's size or position in one kit piece | a rebake of that creation's groups, coarse tier first | seconds |
| A placement moved, added or removed | a rebake of the placements touched | seconds |
| A light or exposure value | no bake | a frame in a second or two |
| The time of day | `world.state.cell.set day $value <t>` with the advance held | immediate; lighting reconverges |

The `lit` stage (the irradiance volume converged) has been the slow one: 117
to 181 seconds after a boot. A sweep doesn't wait for `lit`. The owner judges
form and material at `shown`, and lighting once the volume around the edit has
relit.

## Before the session

- **The machine is the session's.** No other windowed World and no heavy suite
  runs during a pair session; running lanes keep to code and headless work.
  GPU admission waits are the largest avoidable delay.
- **A warm World, booted once.** The lead boots the gallery root
  (`worlds/debug/gallery-root.puck`, or the debug world when the view out
  matters) on the slice's commit before the session, lets it bake and settle,
  and keeps that one World for the whole session. A restart is a bake and a
  settle; an edit is not.
- **Owner input** on the same World: `ownerPlay` (`--devices all`) when the
  owner wants to walk it.
- **Bookmarks.** Named camera poses that match each reference panel (the
  eye-level hall, a plinth close, the arcade, a window bay, the atrium), and
  the time pinned (`day` 0.5, plus an afternoon reading), so each sweep
  captures the same views.
- **The loops read on the slice.** One edit of each kind above, timed with
  `world.iteration` on the gallery root, so the session knows its real
  costs. A loop that takes minutes is an engine gap, fixed before the session.

## Gaps known to cost a sweep

- Hardware-ray probe hits read material 0 from released mesh words, which
  tints interiors orange (open items, Lighting and GI). The fix is in
  progress.
- Glossy floors have no reflection of the room: the prefiltered environment
  and reflections aren't built ([the frame budget](../frame-budget.md)).
- The gallery root has no valley around it, so its windows show white. View-out
  judgements happen in the debug world.
