# Recurring failure shapes

Use these discriminators when planning verification, reviewing a landing, or
diagnosing a multi-lane failure. Turn any recurring hazard into a mechanical
control instead of adding another warning.

## A proof that cannot fail

Force one red: sabotage the thing under test, observe the check fail, and
restore it. If the check cannot go red, do not count it as evidence.

Watch for wildcard-class matchers that accept any transcript, end-state byte
identity offered as proof of a journal count, and forbidden-pattern assertions
aimed at the wrong stream.

## A configuration that cannot expose the defect

Name the configuration the failure requires and run at least one verification
leg in it.

Watch for pixel proofs at the one window size where coordinate spaces coincide,
fresh state directories that cannot exercise upgrades, release events injected
onto already-released buttons, and deletion checks whose base equals their tip.

## An inference presented as an observation

Name the mechanical check behind every claim. Pair an asserted absence with the
literal search that would have found the item. Ask the author about provenance
or production method. Convert a reviewer's hedge into a question the builder
answers by measuring.

Re-check negative results from other sessions before relaying them because their
search scope is not visible in the report.

When you know what to look for, prefer the mechanical check anyway: a targeted
check confirms your hypothesis and stays silent about everything else. When no
mechanical check exists, obtain a count from an independent source — it cannot
find the answer, but it tells you when your pattern is wrong.

## An instrument that reports only the first defect

A refusal is a first-failure statement; a clean pass is a total one. When a
tool reports at most one failure per run, iterate to a clean pass and rest the
completeness claim on that final clean pass, never on the pass count. The
remedy is iteration, not reconfiguration, and the proof's scope is exactly the
set of subjects that produced the clean pass — enumerate that set from an
authoritative source rather than a pattern.

Watch for loaders that report only the first missing member, validators that
stop at the first refusal, and any sweep whose "complete" is really "first
problem fixed."

## A rule that preserves its incident's blind spot

Run the proposed rule against the incident that motivated it, then test the
neighboring shapes it might miss.

Watch for a file-level deletion sweep that misses damage in other files, a
rebase-only rule that misses a non-rebase landing built on a broken tip, and
help text that teaches the vacuous invocation a command was designed to refuse.
If a written hazard recurs, replace or supplement the prose with a mechanical
check.

## Two correct landings that compose into a defect

When concurrent landings touch the same seam, ask what their composition does,
not merely whether each is correct in isolation. Assign someone who holds both
briefs—the lead or a pre-registered reviewer—to exercise the seam.

For example, a store that force-releases buttons on focus loss and a policy
that derives release edges from held state can each be correct alone yet compose
into a focus loss that commits an edit the user never made. Promote the seam's
rule into a mechanism, such as a per-slot system-release counter consumed by the
policy, rather than splitting a warning across two briefs.
